# Beta User Handbook

## Purpose

Phase 3 Milestone 30 Slice C prepares beta users and design partners to evaluate Opportunity OS.

This handbook documents how design partners should join, onboard, review opportunities, and provide feedback. It does not add authentication features, dashboard features, analytics, notifications, payments, CRM integrations, schedulers, workers, or mobile applications.

## Who The Beta Is For

The Private Beta is for approved design partners who can evaluate whether Opportunity OS helps them inspect ranked opportunities, understand evidence, and provide product validation feedback.

Beta users should expect:

- invite-only access
- a protected dashboard experience
- ranked opportunity views
- evidence and provenance views
- save, dismiss, rating, feedback, and bug-report paths
- occasional operator follow-up

Beta users should not expect:

- billing
- production account management
- team administration
- notification preferences
- CRM sync
- mobile app support
- guaranteed data retention beyond the beta operating policy

## Invite Documentation

Invites are controlled by operators.

Each invite should include:

- the design-partner name or approved alias
- the intended recipient
- the beta access window
- the onboarding instructions
- the support intake path
- a reminder not to share invite links or codes

Invite communication must not include secrets, internal API details, database IDs, raw payloads, or unapproved operational notes.

If an invite fails, the user should report:

- approximate time
- safe screenshot if available
- displayed safe error message
- browser and device type

The user should not send tokens, auth headers, raw cookies, passwords, or private data.

## Onboarding Workflow

The onboarding flow is:

1. Receive an approved beta invite.
2. Open the beta dashboard entry point.
3. Confirm the protected dashboard state loads.
4. Review the short beta purpose statement from the operator.
5. Open the opportunity list.
6. Inspect one opportunity detail page.
7. Review ranking explanation, confidence, evidence, and provenance.
8. Save or dismiss at least one opportunity.
9. Submit usefulness, evidence quality, and ranking quality ratings.
10. Submit at least one feedback note or bug report if something is unclear.

Operators may guide this workflow during live design-partner sessions.

## Product Evaluation Guidance

Design partners should focus feedback on:

- whether the opportunity is understandable
- whether ranking feels credible
- whether evidence supports the opportunity
- whether confidence and provenance are useful
- whether search, filters, and pagination support review
- whether saved and dismissed states match expectations
- whether any screen blocks a real evaluation workflow

Feedback should be specific and safe. Avoid sending private customer data, credentials, provider payloads, or screenshots containing secrets.

## Support Expectations

During beta, support is lightweight and operator-managed.

Users can ask for help with:

- invite access
- onboarding
- dashboard navigation
- opportunity interpretation
- feedback submission
- bug reporting

Users should not request:

- billing setup
- production account administration
- CRM integration
- analytics exports
- mobile app setup
- unsupported provider integrations

## Completion

This handbook is complete when beta users can understand access, onboarding, product evaluation, feedback expectations, and support boundaries without requiring new product features.
